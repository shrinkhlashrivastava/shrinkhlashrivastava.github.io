The brief

Hide technical complexity without hiding control.

AngelECHO grew from the AngelPBX ecosystem as an AI communication platform for small and medium businesses — especially teams that cannot staff every call, campaign or after-hours interaction with human agents.

A small developer-created product interface already existed. The redesign aligned it with the broader AngelPBX system while making agent creation, configuration, testing and deployment easier to understand. Platform work and the marketing website moved in parallel; my strongest ownership was on the product platform and 15+ lifecycle email touchpoints, with close collaboration around demo/conversion flow and development.

01 · Product architecture

Start with the agent lifecycle, not the feature list.

Navigation and nomenclature were audited before deeper module design. The resulting structure grouped the product around the work businesses needed to do — create agents, manage knowledge and numbers, run outbound activity, review conversations, analyse performance and administer the account.

  • Dashboard · agents · templates
  • Knowledge Base · phone numbers · outbound calling
  • Call / chat history · analytics
  • Billing · members · roles · activity logs · settings
Show: original navigation → audit → revised structure
02 · Agent creation

One workspace for the decisions that define an AI agent.

Agent configuration brings together name and use case, voice, language, personality, prompt, functions, knowledge, telephony and advanced call settings. The editor was structured so the primary task remained central while deeper controls stayed accessible when needed.

  • Welcome message + core prompt
  • Generate Prompt to reduce blank-state friction
  • Functions and CRM actions
  • Knowledge, speech, call and fallback settings
  • Post-call analysis and webhooks
Show: Agent Editor with focused annotations
03 · Two creation models

Simple agents and complex flows need different levels of control.

A Single Prompt model supported faster natural-language setup, while Conversation Flow provided a visual model for branching and deterministic behaviour.

  • Single Prompt: welcome · prompt · Generate Prompt · settings
  • Conversation Flow: Conversation · Menu/DTMF · Transfer · Custom Function · Hang Up
  • Conditional paths for more advanced behaviours
Show: Single Prompt vs Conversation Flow side by side
04 · Testing loop

Testing belongs inside creation.

The original testing capability existed, but the experience had flow and functionality problems. The redesign kept testing close to configuration so users could iterate without losing context.

05 · Multi-sided product

One ecosystem, different operational perspectives.

Customer, Vendor and Admin platforms shared the same visual language but had different responsibilities. The experience needed to support businesses operating agents, vendors preparing demos and managing prospects, and internal administrators overseeing the wider system within privacy boundaries.

  • Customer — create and operate agents
  • Vendor — manage leads, demos and evaluation
  • Admin — oversee platform operations and account activity
Show: Customer · Vendor · Admin screens
06 · Lifecycle experience

The product journey continued outside the interface.

More than 15 lifecycle email touchpoints were designed to support prospects and customers through demo, evaluation, purchase, onboarding, integration and support. This connected product UX with the surrounding service experience rather than treating email as an afterthought.

  • Pre-demo education and confirmation
  • Demo follow-up and evaluation
  • Proposal, scheduling and purchase
  • Welcome, onboarding and integrations
  • Support, follow-up and renewal communication
Show: Interest → Demo → Evaluate → Purchase → Onboard → Support with selected email thumbnails
07 · Collaboration & launch

Parallel design, close handoff, rapid iteration.

Product and website work moved in parallel across team members, with close developer collaboration throughout. The platform was repeatedly reviewed as functionality was implemented so interaction gaps and inconsistencies could be corrected before they hardened into the product.

  • Close collaboration with website/demo work
  • Developer handoff and clarification
  • Implementation review and functional testing
  • Launch-focused iteration
